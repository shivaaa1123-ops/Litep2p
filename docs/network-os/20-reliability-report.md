# Network OS Reliability Report — Phase 11 baseline

**Status:** measured, reproducible data (master doc §44: no reliability claim
without numbers). Every number below is produced by a deterministic,
seeded run of `desktop/build_fixcheck/bin/churn_simulator` or by
`desktop/build_fixcheck/bin/invariants_test` — commands included so any
number can be regenerated byte-for-byte.

## 1. Method

- The simulator runs the **real engine policy code** — per-peer `ObjectStore`
  (SQLite) + `ReplicaPlanner` — under a virtual clock with injected faults.
  There is no divergent model of the policy (§45 risk control): durability
  transitions, candidate choice, budgets, backoff are all the shipped code.
- **Exact mode** (peers ≤ `--hot-cap`, default 200): every peer is a full
  planner node. **Scaled mode** (peers > 200): 200 planner-driven "hot" peers
  plus capacity-modeled shadow carriers using the same accept/refuse
  thresholds (fidelity recorded per run as `fidelity` in the JSON).
- Determinism: fixed-seed xorshift64*, virtual clock, indexed state.
  Same seed + params ⇒ byte-identical output (asserted in §3).
- Metrics source: `modules/networkos/metrics/ReliabilityMetrics` — bounded,
  deterministic, thread-safe. Energy model constants (mid-range Android,
  recalibrate per device class): 18 mJ/radio-wakeup, 0.35 mJ/CPU-ms,
  1.2 mJ/KB transferred.
- Units note: `wakeups_per_day` counts engine-attributed wakeups per
  **simulated** day at 1 s/tick; treat as a relative cost signal across
  scenarios, not an absolute device prediction.

## 3. Determinism

`churn_simulator --peers 100 --seed 42` run twice ⇒ **byte-identical behavior**
(all counters, delivery stats, gates); only the real wall-clock CPU-time
measurement fields (`cpu_ms_*`, `energy_mj_per_object`) differ between runs by
nature of being measurements. Verified by the harness gate:
`determinism: IDENTICAL (behavior; timing fields excluded)`.

## 4. Scenario results

Baseline delivery reliability and cost — exact mode, 5 seeds per tier
(600 ticks @10/100 peers, 400 ticks @1,000):

| Tier | P(del before TTL) | P(receipt) | median | P95(worst) | wakeups/run | CPU ms/obj | mJ/obj |
|---|---|---|---|---|---|---|---|
| 10 peers   | 1.000 | 1.000 | 30 s | 30 s  | ~160 | 5.6 | 94 |
| 100 peers  | 1.000 | 1.000 | 60 s | 90 s  | ~222 | 4.7 | 129 |
| 1,000 peers| 1.000 | 1.000 | 90 s | 120 s | ~224 | 2.9 | 129 |

Reliability is scale-independent across the exact-mode range; median delivery
grows with inventory-propagation hops (1 hop per maintenance sweep), exactly
the anti-entropy cadence. Per-run planner behavior stays conservative:
e.g. 1,000-peer runs average ~128 repair handoffs vs ~1,301 backoff-suppressed
attempts (no hammering).

Partition/heal ×5 (split t=150, heal t=300): **P(delivery) = 1.000,
P(receipt) = 1.000 in every run**; partition drops are retransferred after
heal; duplicate app deliveries = 0 (anti-entropy converges without re-delivery).

Malicious peers ×5 (10% forgers): **P(delivery) = 1.000**, forged STORED_ACKs
rejected in every run (3–23 per run depending on how many attacks the fault
mix scheduled); durability never raised by a forgery; duplicates = 0.

Replica survival over TTL (churn50 = heavy join/leave, virtual TTL 120 s so
the TTL/2 sampling point lands inside the window): survival at midpoint =
**0.81 / 0.88 / 0.97** (seeds 1–3), P(delivery before TTL) = 0.91–0.97 under
that churn pressure — replicas overwhelmingly outlive the sampling point.

10,000-peer scaled run (hostile_mix: churn+loss+latency+storage+refusal+
corruption+malice, 250 ticks): P(delivery) = 0.594, P(receipt) = 0.947, all
durability gates hold (11 forgeries rejected). The short window plus the full
fault stack bounds throughput; no invariant bends at any scale.

## 5. Tuning with data (§45)

Phase 7 constants under test: `desired_remote_copies=2`,
`retry_base_ms=2000`, `retry_max_ms=300000`, jitter 0.3, repair cooldown 10 s.

Measured verdict: **no constant change is warranted by the first data set.**
- P(delivery before TTL) = 1.0 at baseline; degradation under churn/loss is
  driven by carrier availability, not by retry constants (backoff suppression
  dominates: e.g. 12,428 suppressed vs 110 repair handoffs in the 10-peer
  baseline — the planner is already conservative).
- Over-replication attempts = 0 in every run: the D2 target + max-4 clamp
  holds; loosening the max would only add cost, not reliability.
- Any future constant change must land together with a before/after table
  here (§45: never by intuition).

## 8. Android chaos (§46)

Automated harness: `tools/harness/chaos/` (10 scenarios + orchestrator,
recovery-marker based). Device runs are release-gated when a device is
attached; without one, scenarios SKIP honestly (exit 2) and are recorded in
the phase §10 log. Scenarios: kill, force-stop, Wi-Fi toggle, data toggle,
network switch, reboot, storage fill, clock change, sleep/wake, state
corruption (debug builds).
